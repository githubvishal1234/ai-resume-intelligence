# Security notes

## Authentication and sessions
- Passwords are hashed with argon2id (library defaults). Hashes are upgraded on login when the
  parameters change.
- Unknown accounts are verified against a dummy hash, so login timing does not reveal which
  accounts exist. Login errors are always generic.
- Sessions are opaque random tokens. Only their SHA-256 is stored, so a database leak does not
  yield usable cookies.
- The session cookie is `HttpOnly` and `SameSite=Lax`. It is `Secure` when
  `SESSION_COOKIE_SECURE=true`, which production requires.
- Sessions have an absolute TTL (default 7 days) and an idle TTL (default 24 hours). Expired
  sessions are deleted when presented, and in bulk on every successful login.
- CSRF uses a per-session token, required in `X-CSRF-Token` on every non-GET request that
  needs auth. It is enforced in the shared auth dependency.

## Rate limiting
- Login is limited per client IP and per account (hashed email). Registration is limited per IP.
- **Limitation:** state is in-process. With N API replicas, the effective limit is N times
  higher. Replace it with a shared store before scaling out.
- **Behind a proxy:** uvicorn must trust the proxy's `X-Forwarded-For` (`--proxy-headers
  --forwarded-allow-ips`, set through `FORWARDED_ALLOW_IPS`). Otherwise every user shares the
  proxy IP and one attacker can lock out all logins.
- **Known trade-off:** anyone who knows an email can temporarily lock that account out of
  login (10 attempts in 5 minutes by default).

## Known trade-offs
- `POST /auth/register` returns `409 EMAIL_ALREADY_REGISTERED`, which reveals that an account
  exists. This was kept for usability. Without an email provider (D-07), there is no
  "check your inbox" flow that would hide it.

## Data handling
- Logs never include request bodies, passwords, tokens, or resume and job-description text.
  Only the path is logged, never the query string.
- Validation errors never echo submitted values.
- The audit log records auth events without emails or other PII in `details`.
- Storage keys are generated by the server and validated. The local backend rejects path
  traversal and symlink escapes.

## File uploads (resumes)
- Only PDF, DOCX and TXT are accepted. The extension must match the magic bytes; the
  client's MIME type is ignored.
- The size cap (`MAX_UPLOAD_BYTES`) is enforced while reading. PDFs over 10 pages and text over
  60,000 characters are refused or truncated.
- Encrypted PDFs, DOCX files that contain `vbaProject.bin` (macros), and DOCX archives over
  25 MB uncompressed (zip bombs) are rejected.
- Storage keys are `users/<id>/resume-files/<random>.<ext>`. The original filename is
  sanitized and used only for display and download.
- Rejected uploads store nothing. If the database write fails after storage, the stored file
  is deleted.
- Every resume and import route checks ownership through `ensure_access`. Other users' items
  return 404. Tests cover all 12 endpoints.
- Text is extracted in-process with pure-Python libraries, without shelling out. Moving
  extraction to a sandboxed worker is planned for Phase 9.

## Production configuration guards
With `APP_ENV=production`, the app refuses to start when:
- the development database password is in use,
- `SESSION_COOKIE_SECURE` is false, or
- `CORS_ORIGINS` contains `*`.

## Tests
The test suite drops and truncates tables. It reads only `TEST_DATABASE_URL` and refuses to run
unless the database name ends in `_test`.
