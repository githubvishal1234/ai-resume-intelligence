# Security notes

## Authentication and sessions
- Passwords are hashed with argon2id (library defaults). Hashes are upgraded on login when the
  parameters change.
- Unknown accounts are verified against a dummy hash, so login timing does not reveal which
  accounts exist. Login errors are always generic.
- Sessions are opaque random tokens. Only their SHA-256 is stored, so a database leak does not
  yield usable cookies.
- The session cookie is `HttpOnly` and `SameSite=Lax`. It is `Secure` when
  `SESSION_COOKIE_SECURE=true`, which production requires.
- Sessions have an absolute TTL (default 7 days) and an idle TTL (default 24 hours). Expired
  sessions are deleted when presented, and in bulk on every successful login.
- CSRF uses a per-session token, required in `X-CSRF-Token` on every non-GET request that
  needs auth. It is enforced in the shared auth dependency.
- Password reset (only when email is configured): the request answers the same whether or not
  the address has an account, and is rate limited per IP and per address. Links are
  single-use, expire (`PASSWORD_RESET_TTL_MINUTES`, default 30), and only the token's SHA-256
  is stored. A new request replaces older links; a reset signs out every session. The reset
  page removes the token from the address bar, and `Referrer-Policy: no-referrer` is set.
  Known limit: a request for a real account takes a little longer (it sends mail), so
  response timing can hint that an account exists.
- SMTP errors are logged by type only; server replies can echo addresses or credentials.
- Changing the password requires the current one and signs out every other session. Users can
  list their sessions (never the token) and end any of them. Password checks on `/account`
  share the auth rate limit.

## Rate limiting
- Login is limited per client IP and per account (hashed email). Registration is limited per IP.
- **Limitation:** state is in-process. With N API replicas, the effective limit is N times
  higher. Replace it with a shared store before scaling out.
- **Behind a proxy:** uvicorn must trust the proxy's `X-Forwarded-For` (`--proxy-headers
  --forwarded-allow-ips`, set through `FORWARDED_ALLOW_IPS`). Otherwise every user shares the
  proxy IP and one attacker can lock out all logins.
- **Known trade-off:** anyone who knows an email can temporarily lock that account out of
  login (10 attempts in 5 minutes by default).

## Known trade-offs
- `POST /auth/register` returns `409 EMAIL_ALREADY_REGISTERED`, which reveals that an account
  exists. This was kept for usability. Without an email provider (D-07), there is no
  "check your inbox" flow that would hide it.

## Data handling
- Logs never include request bodies, passwords, tokens, or resume and job-description text.
  Only the path is logged, never the query string.
- Validation errors never echo submitted values.
- The audit log records auth events without emails or other PII in `details`.
- Account deletion requires the password and is immediate: the user row and everything owned
  by it are deleted by cascading foreign keys, then the stored files. The audit entry keeps
  only the old user id as the resource, not as the actor. No retention policy is applied (D-08).
- Storage keys are generated by the server and validated. The local backend rejects path
  traversal and symlink escapes.

## File uploads (resumes)
- Only PDF, DOCX and TXT are accepted. The extension must match the magic bytes; the
  client's MIME type is ignored.
- The size cap (`MAX_UPLOAD_BYTES`) is enforced while reading. PDFs over 10 pages and text over
  60,000 characters are refused or truncated.
- Encrypted PDFs, DOCX files that contain `vbaProject.bin` (macros), and DOCX archives over
  25 MB uncompressed (zip bombs) are rejected.
- Storage keys are `users/<id>/resume-files/<random>.<ext>`. The original filename is
  sanitized and used only for display and download.
- Rejected uploads store nothing. If the database write fails after storage, the stored file
  is deleted.
- Every resume and import route checks ownership through `ensure_access`. Other users' items
  return 404. Tests cover all 12 endpoints.
- Text is extracted in-process with pure-Python libraries, without shelling out. A sandboxed
  extraction worker was considered in Phase 9 and deferred. It needs worker infrastructure,
  which depends on hosting (D-06). The size, page, archive-size and macro limits above bound
  the work a single upload can cause.

## AI providers
- The providers are Groq and OpenAI (D-03), both in `app/ai/providers/openai.py` (they share
  the OpenAI API format). It is the only module that calls a vendor API. It uses the standard library, so no vendor SDK is installed. Every AI action
  goes through `get_llm_provider`, which returns `503 AI_PROVIDER_NOT_CONFIGURED` until
  `LLM_PROVIDER`, `LLM_MODEL` and `LLM_API_KEY` are all set.
- The key is a `SecretStr` read from the environment. It is never logged, and error messages
  and logs from the adapter carry only the HTTP status, never the key, prompt or answer.
- Provider failures return `502 AI_PROVIDER_FAILED`, and answers that fail schema validation
  return `502 AI_OUTPUT_INVALID`. Neither saves anything, so earlier results stay intact.
- Resume, job, question and answer text is passed to the model as data in user messages,
  never in the system prompt. Tests check this for tailoring rewrites and interview feedback.
- Model output that changes a resume goes through the same factual check as user edits.
- Every AI call is recorded in `ai_usage` (user, feature, provider, model, token counts,
  latency, outcome), never with prompt or answer text, and capped per user per day
  (`AI_DAILY_LIMIT_PER_USER`). Rows are deleted with the user.
- AI resume import keeps only values that appear in the uploaded file's text, so the model
  cannot add facts to a resume; what it tried to add is shown to the user.
- Layer 2 of that check (`app/tailoring/claims.py`) asks the model to quote supporting words
  from the master resume and verifies each quote itself, so the model cannot vouch for a claim
  without real evidence. Its findings are warnings; layer-1 flags still block.

## Security review (Phase 9, 2026-10-12)
- **Route sweep** (`tests/test_security_sweep.py`): every operation in the OpenAPI schema is
  called without a session and must answer `401 AUTH_REQUIRED` with a request id. Every unsafe
  method is called with a session but no CSRF header and must answer `403 CSRF_INVALID`.
  Only the routes on an explicit allowlist (health, capabilities, register, login, logout)
  are public. New routes are covered automatically.
  - Found and fixed: `GET /output/templates` answered without a session. It returned only
    template names, but it now needs a session like every other app route.
- **Ownership:** every resource module has IDOR tests in which a second user tries every
  endpoint and gets 404: resumes, jobs, matches, tailoring, output, applications,
  notifications and interview prep.
- **Dependencies:** `pip-audit` (runtime lock) and `npm audit` (all dependencies) found no
  known vulnerabilities. Both run in CI.
- **Headers:** the API sends `nosniff`, `DENY` framing, `no-referrer`, `no-store` and a
  `default-src 'none'` CSP on every response, including errors and 404s (tested). nginx sends
  the SPA's CSP. HSTS belongs at the TLS terminator (see DEPLOYMENT.md).
- **Still open, by decision:** the in-process rate limiter (single-process limit), the
  register enumeration trade-off, and the in-process file extraction described above.

## Production configuration guards
With `APP_ENV=production`, the app refuses to start when:
- the development database password is in use,
- `SESSION_COOKIE_SECURE` is false, or
- `CORS_ORIGINS` contains `*`.

## Tests
The test suite drops and truncates tables. It reads only `TEST_DATABASE_URL` and refuses to run
unless the database name ends in `_test`.
