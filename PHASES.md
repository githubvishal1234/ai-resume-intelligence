# Phase-wise delivery plan

This file is where phase status is tracked. `docs/ROADMAP.md` lists scope, and
`docs/PRODUCTION_IMPLEMENTATION_PLAN.md` holds the original architecture proposal.

**Rules**
- A phase is "Done" only when its exit checks pass: backend tests, ruff, mypy, frontend
  typecheck, lint, tests and build.
- Nothing is faked. Some features need a pending company decision, such as the LLM provider
  (D-03). Those ship with a working deterministic version where a sound one exists. Otherwise
  they show an honest "not configured" state and get a provider seam.
- The master resume is never changed by analysis, matching or tailoring. Only an explicit user
  edit creates a new master version.

## Phase 2: Master Resume

**Delivered**
- [x] Upload PDF / DOCX / TXT. Checks cover extension vs magic bytes, a 10 MB cap, a 10-page cap
      and a text-length cap. Encrypted PDFs, macro-enabled Word files, legacy `.doc` files and
      zip bombs are rejected. Storage keys are generated by the server, and the filename is
      sanitized for display only.
- [x] Deterministic text extraction (pypdf, python-docx) and a heuristic parser (`heuristic-v1`).
      It covers contact, summary, experience, education, skills (with groups), projects,
      certifications and other sections. It only copies text from the file and never invents
      anything (tested). Each section gets a confidence level, notes, and warnings when no
      headings are found.
- [x] Review screen before anything is saved. The user can edit every section and see
      low-confidence and missing-section notices. They can then save or discard.
- [x] Master resume editor (add, remove and reorder entries; bullets one per line; grouped
      skills). It warns about unsaved changes and rejects saves based on an old version with
      `VERSION_CONFLICT`.
- [x] Immutable versions. Every upload, edit or restore appends a version, and a database
      trigger rejects UPDATEs. The version history includes a preview, restore (creates a new
      version) and a download of the original upload.
- [x] Exactly one active master per user, enforced by a partial unique index and the service.
      Creating a resume from scratch is supported.
- [x] My Resumes page. User-initiated delete removes the versions and stored files.
- [x] Rule-based resume analysis (`rules-v1`): 14 checks covering contact, summary, dated
      roles, bullet count, quantified results, action verbs, concise bullets, first-person
      pronouns, education, skills and length. Each check comes with an explanation. The score
      is clearly labelled as a conventions score, not a hiring prediction.
- [x] Entities have stable ids, so later evidence and tailoring can point at them. The editor
      keeps those ids when you edit.

**Not done here, by decision**
- AI-assisted parsing waits on D-03. The parser interface is ready for it.
- OCR for scanned PDFs is out of scope. Those files fail with a clear message.
- Background worker: parsing runs synchronously within strict size and page limits. Move it to
  a worker if it becomes slow.

**Verified 2026-10-12**
- 86 backend tests pass. Phase 2 added tests for parser accuracy and the no-invention rule,
  every rejection path, versioning and conflicts, the DB immutability trigger, the
  one-master index, and IDOR on all 12 resume and import endpoints.
- 36 frontend tests pass. Lint, types and the build are clean, and the API types are in sync.
- Browser run: register → upload a PDF → review (all sections parsed) → save → edit → save
  (v2) → restore v1 (v3) → analysis (95/100). No console errors, and no overflow at 768 or 390.
- Fixed during verification: after a successful save, the unsaved-changes guard blocked the
  navigation away from the editor.

## Phase 3: Job Intelligence

**Delivered**
- [x] Add a job by pasting text (50 to 50,000 characters) or uploading a PDF / DOCX / TXT file.
      Uploads reuse the Phase 2 file checks. Title, company and location are optional; the title
      is taken from the posting when left empty.
- [x] Links: `POST /jobs/from-url` goes through the job-source adapter registry. No source is
      approved yet (D-05), so every link returns `JOB_SOURCE_NOT_SUPPORTED`. The UI then offers
      to paste the description instead and keeps the link with the saved job.
- [x] Deterministic analysis (`jd-rules-v1`):
  - Requirements split into required / preferred / nice-to-have, using the posting's own
    section headings and wording ("preferred", "a plus"). Without headings it works sentence
    by sentence and says so.
  - Each requirement has a category (skill, experience, education, certification) and the
    skills it mentions. Responsibilities, "about us" and benefits are kept out of requirements.
  - Key facts only when stated: minimum years, education level, seniority, employment type,
    work mode, salary.
  - Frequent terms, leaving out skills and the company's own name.
  - Requirement ids come from the requirement text, so they are stable across re-analysis
    (Phase 4 evidence will point at them).
- [x] Skills vocabulary (`app/skills/vocabulary.py`): about 200 canonical skills with
      categories and aliases (Postgres → PostgreSQL, k8s → Kubernetes). Names that are also
      English words (Go, R, Spring, Express…) only count when correctly cased.
- [x] Job Analyzer pages: list, "Analyze a job" (Paste / Upload / Link tabs), and a job detail
      page with facts, requirements by tier, skills by tier, responsibilities, the source and the
      original text. Details can be edited, analysis re-run and the job deleted.
- [x] Job Analyzer is enabled in the navigation, and the dashboard step links to it.

**Not done here, by decision**
- Fetching postings from job sites waits on D-05 (which sites, on what terms). Adding one is a
  single `JobSourceAdapter` plus a registry entry.
- AI-assisted requirement extraction waits on D-03. The analyzer output is a plain model, so a
  provider-backed analyzer can produce the same shape.
- Uploaded JD files are not stored; only their extracted text is kept.

**Verified 2026-10-12**
- 106 backend tests pass (20 new: vocabulary, tiers and facts, no invented facts, stable ids,
  paste/upload/link, validation, edit, re-analyze, delete, auth and CSRF, IDOR on all job
  endpoints). ruff, `ruff format --check` (now in CI) and mypy are clean.
- 42 frontend tests pass. Lint, types and the build are clean, and the API types are in sync.
- Browser run: dashboard → Analyze a job → link refused → paste fallback (link kept) →
  analysis (5 required, 3 nice-to-have, Senior, 5+ years, Bachelor's, Full-time, Hybrid,
  ₹35-45 LPA) → edit details → re-run → list → upload a .txt JD → delete. No console errors
  besides the expected 422, and no overflow at 1440, 1024, 768 or 390.
- Fixed during verification: the company's name showed up as a "frequent term".

## Phase 4: Matching & Skill Gaps

**Delivered**
- [x] Rule-based matcher (`match-rules-v1`) between the master resume's current version and a
      job's analysis. It only reads both; a test proves the master is unchanged.
- [x] Evidence per requirement: strong / partial / missing, with a plain reason and quotes
      from the resume entities behind it (by entity id).
  - Skills are **strong** when a role or project shows them, **partial** when they are only
    listed. "A or B" requirements are met by either.
  - Years are computed from dated roles (overlaps counted once; undated roles reported).
  - Education compares degree levels; certifications look for a matching listed one.
  - Requirements without a known skill fall back to word overlap, and say so.
- [x] Subscores with explanations: Skills (required 3×, preferred 2×), Experience, Keywords,
      Education, and Resume quality (the Phase 2 checks). Weights 40/20/15/10/15 are an
      engineering default (D-11). Parts that don't apply to a job are left out and the rest
      renormalized, instead of scoring zero.
- [x] Skill gap matrix with four severities: critical (required, missing), high (preferred,
      missing), medium (required, only listed), low (nice-to-have, preferred-but-listed, or met
      by an alternative).
- [x] Each run is stored as a snapshot with the resume version and method versions. It is
      marked "out of date" when the resume gets a new version or the rules change.
- [x] Pages: Job Match (jobs with their latest score), match detail (score, breakdown,
      requirements by tier with evidence, missing frequent terms), Skill Gap Matrix. Both nav
      items are enabled, the job page has "Match my resume", and the dashboard links to it.

**Not done here, by decision**
- Semantic (embedding or LLM) matching waits on D-03. The matcher output is a plain model, so
  a provider-backed matcher can add to it.
- Scoring weights stay a default until D-11 is decided; they live in one table (`WEIGHTS`).

**Verified 2026-10-12**
- 119 backend tests pass (13 new: date parsing, overlap counting, evidence statuses, evidence
  ids point at real entities, severities and alternatives, renormalized subscores, empty
  resume, master-required, snapshot + master unchanged, stale after edit, IDOR including
  matching someone else's resume, cascade on job delete). ruff, format and mypy are clean.
- 47 frontend tests pass. Lint, types and the build are clean, and the API types are in sync.
- Browser run: job without a resume → "add your master resume first" → upload master →
  Job Match → run (84/100; required 4 of 5 met) → Skill gaps (1 medium, 4 low, 4 no gap) →
  edit the resume → match shows "out of date" → re-run (85/100). No console errors besides the
  expected 401 before sign-up, and no overflow at 1440, 1024, 768 or 390.
- Fixed during verification: a never-matched job produced a 404 in the console (the endpoint
  now returns null), and the gap table scrolled sideways on phones.

## Phase 5: Tailoring

- Tailoring sessions with proposed changes. Each change records the original text, the
  proposal, the reason, the requirement it serves and the evidence behind it.
- Deterministic tailoring operations that need no LLM: reorder skills and bullets by
  relevance, and surface keywords that already exist in the master.
- LLM rewrites run only when a provider is configured (D-03).
- Factual-consistency layer 1 (deterministic): unsupported numbers, technologies, employers
  and dates are flagged.
- An Accept / Reject / Edit review flow. Finalizing creates a tailored resume, and an
  invariant test proves the master is unchanged.

## Phase 6: Resume Output

- ATS checks on the tailored resume.
- A small set of ATS-safe templates (D-10).
- Text-extractable PDF export and download through an authenticated endpoint.

## Phase 7: Applications

- An application tracker: company, role, URL, resume version, status and notes, with an
  event history. CRUD, authorization tests and in-app notifications.

## Phase 8: Interview Prep

- Question banks built from the job requirements, the tailored resume and skill gaps
  (deterministic templates).
- A practice-session flow with notes.
- LLM answer evaluation only when a provider is configured.

## Phase 9: Hardening

- Security review, dependency audit, performance checks, observability, deployment
  contract (`docs/DEPLOYMENT.md`), backups.
